## Open a project brief

<details>
<summary><strong>01 / Engineering Intelligence Platform</strong> · Git analytics, health signals, team risk</summary>

<br/>

<img src="https://img.shields.io/badge/PROBLEM-Too%20much%20raw%20Git%20data-102A40?style=flat-square&labelColor=00BFD9" alt="Problem"/>

**Goal:** turn repository activity into engineering signals people can inspect, challenge, and use.

| Layer | Design / implementation focus |
|---|---|
| Data ingestion | GitHub API integration, pagination, rate limits, repository history |
| Analysis | Repository health, ownership signals, team balance, hotspots, contribution patterns |
| Backend | Spring Boot analysis services and report-oriented endpoints |
| Frontend | Angular dashboards, comparison views, employee profiles, risk panels |
| Trust | Real Git data, clear metric definitions, drill-down verification, no fabricated numbers |

**Architecture path**

`GitHub repositories → ingestion → analysis services → report API → Angular insights`

**Engineering lessons:** LOC alone is not productivity; ownership signals need context; metrics need scope and evidence; ingestion must handle API limits and incomplete history.

<sub>Angular · TypeScript · Spring Boot · GitHub API · SQL · GitHub Actions</sub>
</details>

<details>
<summary><strong>02 / Identity, RBAC & Organisational Scoping</strong> · Authentication beyond the login screen</summary>

<br/>

<img src="https://img.shields.io/badge/FOCUS-Server--side%20authorization-102A40?style=flat-square&labelColor=00BFD9" alt="Authorization"/>

**Goal:** a signed-in user can access only the actions and organisational data allowed by their permissions and scope.

| Layer | Design / implementation focus |
|---|---|
| Authentication | JWT validation and authenticated principal construction |
| Authorization | Standard roles plus granular permission authorities |
| Scoping | Hierarchical organisational boundaries applied to data access |
| API layer | Explicit access checks, not frontend-only restrictions |
| Verification | Phase checkpoints and evidence-based security closure |

**Request path**

`JWT → principal → roles + permissions → organisation scope → endpoint/data access`

Authentication answers *who are you?* Authorization and scoping answer *what can you do, and which data can you see?*

<sub>Java · Spring Boot · Spring Security · JWT · RBAC · REST</sub>
</details>

<details>
<summary><strong>03 / Multi-sided Commerce Platform</strong> · Customer, merchant and admin workflows</summary>

<br/>

<img src="https://img.shields.io/badge/FOCUS-Role--specific%20product%20flows-102A40?style=flat-square&labelColor=00BFD9" alt="Commerce"/>

**Goal:** keep three user journeys coherent without turning the backend into unrelated endpoints.

| Surface | Responsibility |
|---|---|
| Customer app | Discovery and customer-facing actions |
| Merchant app | Merchant-side operational workflows |
| Admin panel | Oversight, management, and administrative actions |
| API | Validation, business rules, consistent response contracts |
| Database | Relational persistence and connected domain records |

**System path**

`Customer / Merchant / Admin → role-aware APIs → Spring Boot services → PostgreSQL`

<sub>Mobile-first UX · Spring Boot · PostgreSQL · REST APIs</sub>
</details>

<details>
<summary><strong>04 / KYC & Operations Analytics</strong> · Operational dashboards and reporting</summary>

<br/>

<img src="https://img.shields.io/badge/FOCUS-Operational%20clarity-102A40?style=flat-square&labelColor=00BFD9" alt="Operations"/>

**Goal:** make record-heavy workflows easier to review, filter, track, and report on.

- Status-oriented dashboard cards and filters
- Data grids with sorting and review workflows
- Analytics components tied to operational states
- CSV, Excel, and PDF export workflows
- Frontend states aligned with backend status definitions

**Flow:** `Operational records → status rules → filters + data grid → dashboard → export`

<sub>Angular · Angular Material · AG Grid · TypeScript · SQL</sub>
</details>

<details>
<summary><strong>05 / Personal Companion</strong> · Privacy-first, local-first computing</summary>

<br/>

<img src="https://img.shields.io/badge/FOCUS-User%20control%20%2B%20modularity-102A40?style=flat-square&labelColor=00BFD9" alt="Personal companion"/>

**Goal:** explore a companion architecture across Android and desktop while treating privacy, operating context, and power use as design requirements.

| Area | Design direction |
|---|---|
| Modes | Offline, online, hybrid, focus, driving, meeting, gaming, sleep, low-power, do-not-disturb |
| Modularity | Separate platform concerns and mode behavior |
| Android | Jetpack Compose interface |
| Shared code | Kotlin Multiplatform modules |
| Product values | User control, privacy boundaries, predictable behavior |

**Architecture lens:** define modes explicitly, keep responsibilities modular, and make transitions understandable rather than burying them in scattered conditionals.

<sub>Kotlin · Kotlin Multiplatform · Jetpack Compose · Android</sub>

## System architecture

<img src="https://raw.githubusercontent.com/janarthananRaja/janarthananRaja/main/architecture-map.svg" width="100%" alt="Engineering architecture map"/>

<details>
<summary><strong>Open the architecture principles</strong></summary>

- **Contracts:** define how UI, APIs, services, and data fit together.
- **Access:** keep identity, permissions, and data scope explicit.
- **Failure paths:** handle invalid input, missing access, upstream errors, and empty results deliberately.
- **Evidence:** keep metrics traceable to their source and calculation.
- **Maintainability:** separate responsibilities so changes do not ripple through the whole system.
</details>
